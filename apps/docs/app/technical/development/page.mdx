# Développement

## Démarrage

```bash
pnpm install
pnpm packages:build   # @remi/ui et @remi/services doivent exister avant qu'une application compile
pnpm web:dev          # ou admin:dev / marketing:dev / docs:dev
```

`turbo run dev` déclare `dependsOn: ["^build"]` : un simple `pnpm dev` construit donc d’abord les packages.
Lancez `pnpm packages:dev` dans un second terminal pour les reconstruire à chaque modification.

## L’usine possède les contrôles

Le formatage, le lint, le typecheck et le build sont un travail déterministe, sans IA. Ils appartiennent à Husky, à la CI et à
la préversion Vercel — pas à la fenêtre de contexte d’une session. Un agent qui travaille dans ce dépôt ne peut pas
les lancer en local : `.claude/hooks/block-local-checks.sh` le bloque. On pousse, puis on relit le résultat dans les
check runs de la PR.

Quel contrôle tourne où tient dans un seul tableau, qui vit dans `/CONVENTIONS.md` § « The factory owns the
checks — you do not ». Il n’est pas recopié ici, car une seconde copie est la façon dont les deux se mettent à
diverger.

## CI/CD

Chaque application se déploie depuis son propre projet Vercel, filtré par `turbo-ignore` pour qu’une modification de `apps/docs`
ne reconstruise pas `apps/web`. Le cache distant Turborepo est partagé entre la CI et Vercel : les
builds de packages dont la CI a besoin pour `typecheck` sont donc le plus souvent restaurés plutôt que recompilés.

## Livraison

Le travail atteint `main` par le pipeline. `/pipeline scope` règle une demande avec l’opérateur dans
`scope.md` et découpe le lot d’intake ; ensuite, par ébauche, `new` → `build` → `release` — une PR de fonctionnalité,
deux portes humaines (Spec approved, Ready to merge), et un squash-merge qui emporte le dossier du run et
son archive. Une voie rapide `bug` / `tweak` / `chore` saute le début et se termine par une PR que l’opérateur
fusionne ; `knowledge` modifie une de ces pages en dehors d’une Release. Voir `.icm/CONTEXT.md`.
