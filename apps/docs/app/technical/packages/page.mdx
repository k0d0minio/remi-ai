# Packages

Deux packages, et la flèche de dépendance ne pointe jamais que **application → package**.

Les règles complètes de chaque package vivent à côté de son code, et c’est cette copie qui fait foi : `packages/ui/AGENTS.md`
et `packages/services/AGENTS.md` changent dans le même commit que ce qu’ils décrivent. Cette page est
l’orientation — à quoi sert chaque package, et le seul fait à son sujet sur lequel on se trompe facilement.

## `@remi/ui`

Toutes les primitives partagées entre applications. shadcn/ui New York sur Radix, Tailwind 4.

`tsup.config.ts` produit **quatre** unités de build, et chaque découpage est porteur :

| Chemin d’import   | Bannière       | Appelable depuis       |
| ----------------- | -------------- | ---------------------- |
| `@remi/ui`        | `"use client"` | composants client      |
| `@remi/ui/server` | aucune         | serveur **et** client  |
| `@remi/ui/utils`  | aucune         | serveur **et** client  |
| `@remi/ui/motion` | `"use client"` | composants client      |

`cn()` vit sur `/utils`. Fusionner cette entrée dans le barrel casse `cn()` dans chaque composant serveur
du dépôt ; fusionner `/server` dedans fait renoncer aux RSC sur le site marketing. tsup **embarque** chaque
entrée, si bien que tout ce qu’une entrée peut atteindre y est intégré — les deux sens d’import qui cassent
silencieusement le découpage sont documentés dans `packages/ui/AGENTS.md` et appliqués par des zones `no-restricted-imports` dans
`eslint.config.ts`.

Les tokens sont livrés en deux feuilles de style : `@remi/ui/tokens.css` (brute, sans Tailwind — celle que chaque application de ce
dépôt importe) et `@remi/ui/globals.css` (un build Tailwind + tokens autonome, pour un consommateur qui
n’exécute aucune passe Tailwind de son côté). Les applications ne redéfinissent jamais un token.

## `@remi/services`

Le stockage, l’e-mail, l’IA et le lecteur d’environnement. Chacun est un **point de jonction**, pas une intégration : une interface
plus un appel `register*()`, l’adaptateur concret étant enregistré une seule fois au démarrage du processus par l’application qui
possède le processus. Seul l’e-mail a retenu un fournisseur jusqu’ici (Resend) ; choisir plus tard une base de données ou un fournisseur
d’IA revient donc à un nouveau fichier plus une ligne d’enregistrement — jamais à une réécriture des appelants. Le tableau
des points de jonction — interface, appel d’enregistrement, et ce qui se passe quand rien n’est enregistré — se trouve dans
`packages/services/AGENTS.md`.

Choisissez le point d’entrée qui correspond à l’endroit où le code s’exécute :

| Import                  | S’exécute sur         |
| ----------------------- | --------------------- |
| `@remi/services/shared` | navigateur + serveur  |
| `@remi/services/server` | serveur uniquement    |
| `@remi/services/db`     | serveur uniquement    |
| `@remi/services/ai`     | serveur uniquement    |
| `@remi/services/email`  | serveur uniquement    |

Le barrel racine `@remi/services` ne contient que des types, et le lint interdit aux applications de l’importer ; le
choix est donc toujours explicite à l’endroit de l’appel. Ce que porte chaque point d’entrée, et pourquoi le registre d’un point de jonction
appartient au point d’entrée par lequel on l’a atteint, se trouve dans `packages/services/AGENTS.md`.

`patientContextText()` est le seul export qui se trouve sur deux d’entre eux. Il assemble le contexte
pseudonymisé d’un patient — profil, objectifs, consigne courante, recommandations actives, suppléments
et essentiels — en texte français simple, par lequel s’ouvre un prompt d’IA, et c’est une fonction pure : pas
d’E/S, pas d’horloge, pas de fournisseur. Il vit sous `src/ai/` parce que c’est son usage, et il est
réexporté depuis `/shared` ainsi que depuis `/ai` et `/server` parce qu’il est réellement isomorphe — la
console réassemble le texte dans le navigateur pendant que l’opérateur le modifie, et l’atteindre par
`/ai` depuis un composant client ferait entrer le point de jonction du fournisseur dans ce bundle. Son type d’entrée n’a
aucun champ pour un vrai nom, un e-mail ou un jeton de partage : la pseudonymisation est donc une propriété de la signature
plutôt que de la mémoire de l’appelant.
