# Applications

Six apps, one Vercel project each, one port each. Every app that renders product UI consumes
`@remi/ui` and owns no primitives of its own.

| App         | Package            | Port | Auth | Data                       | Purpose                                       |
| ----------- | ------------------ | ---- | ---- | -------------------------- | --------------------------------------------- |
| `web`       | `@remi/web`        | 3000 | yes  | `@remi/services/server`    | The product. Signed-in surface.               |
| `marketing` | `@remi/marketing`  | 3001 | no   | mostly static              | The public site. Indexable, content-led.      |
| `admin`     | `@remi/admin`      | 3002 | yes  | `@remi/services/server`    | Internal operations. Operator-only.           |
| `docs`      | `@remi/docs`       | 3003 | no   | none                       | This site. Nextra, MDX.                       |
| `support`   | `@remi/support`    | 3004 | no   | typed content modules      | The public help centre. Indexable, anonymous. |
| `demo`      | `@remi/demo`       | 3005 | no   | **mock only**              | The Design stage's prototype sandbox.         |

## Why admin is its own app, not a route group in web

A separate deployment gives a separate URL, separate environment variables, and separate access
control. A `/admin` route group inside the product app makes every operator-only capability one
routing mistake away from a customer.

## The operator's patient page

A patient's page opens on a working view — what an operator reaches before anything else: the
status line, the active goals, the standing instruction, the head of the living summary, the most
recent meals, the main recommendations, a preparation note for the next consultation, and four
quick actions. Everything else sits behind navigation: a section index in the right rail on
desktop, a segmented control (Suivi · Journal · Dossier · Profil) on phone, and a horizontal row
of anchors in between. One DOM order, three views — the secondary sections' bodies are unchanged.

### Writing up a consultation

The first quick action leaves the page: `/patients/[id]/consultation` is the post-consultation
write-up, laid out in the order the work happens — the note, a check-in per active goal, the
standing instruction and the living summary prefilled with what is in force, links into the
recommendation, supplement and essentials sections, and the preparation note for next time. One
save writes all of it in a single transaction and records a single audit event naming what changed;
the per-card actions on the patient page remain the between-consultation edit path.

The form is kept in the browser's local storage while it is typed and restored when the screen
reopens — the links into the protocol sections leave the page and come back, and a draft that
survives only the note would lose the rest. It is cleared once a save succeeds, and nothing about it
reaches the server or another device.

## Why demo can never reach a backend

The Design stage merges demo work straight to the live URL so a stakeholder reviews the real
deployed thing. That is only safe while the demo cannot touch a real record. Three independent
guards enforce it: `@remi/services` is absent from its `package.json`, absent from
`transpilePackages`, and blocked by ESLint. A feature that needs real data has outgrown the demo.
