# Applications

Quatre applications, un projet Vercel chacune, un port chacune. Toute application qui affiche une interface produit consomme
`@remi/ui` et ne possède aucune primitive en propre.

| Application | Package           | Port | Auth | Données                 | Rôle                                         |
| ----------- | ----------------- | ---- | ---- | ----------------------- | -------------------------------------------- |
| `web`       | `@remi/web`       | 3000 | oui  | `@remi/services/server` | Le produit. Surface connectée.               |
| `marketing` | `@remi/marketing` | 3001 | non  | surtout statique        | Le site public. Indexable, porté par le contenu. |
| `admin`     | `@remi/admin`     | 3002 | oui  | `@remi/services/server` | Opérations internes. Opérateur uniquement.   |
| `docs`      | `@remi/docs`      | 3003 | non  | aucune                  | Ce site. Nextra, MDX.                        |

## Pourquoi admin est une application à part, et non un groupe de routes dans web

Un déploiement séparé donne une URL séparée, des variables d’environnement séparées et un contrôle d’accès
séparé. Un groupe de routes `/admin` dans l’application produit place chaque capacité réservée aux opérateurs à une
erreur de routage d’un client.

## La page patient de l’opérateur

La page d’un patient s’ouvre sur une vue de travail — ce qu’un opérateur consulte avant tout : la
ligne de statut, les objectifs actifs, la consigne permanente, le début du résumé vivant, les repas les plus
récents, les recommandations principales, une note de préparation pour la prochaine consultation, et quatre
actions rapides. Tout le reste est derrière la navigation : un index des sections dans le rail de droite sur
ordinateur, un contrôle segmenté (Suivi · Journal · Dossier · Profil) sur téléphone, et une rangée horizontale
d’ancres entre les deux. Un seul ordre du DOM, trois vues.

Les sections secondaires sont façonnées pour la manière dont un opérateur les lit, plutôt que pour la manière dont les
lignes sont stockées. L’anamnèse liste les domaines déjà renseignés, le reste étant proposé sous la forme d’une
courte rangée d’invites à compléter. Le profil est un résumé en lecture — identité, mesures, alimentation,
consentement — avec le formulaire complet à un clic derrière. **Tout ce qui n’est plus actif est un pli fermé
qui porte son compte** au pied de la section dont il relève : recommandations archivées, essentiels
archivés, recettes précédentes, repas archivés, suppléments arrêtés, observations archivées, objectifs
archivés, et le flux de suppression à la fin du profil. Il n’y a ni section « archivé » autonome
ni carte de danger séparée, de sorte que la liste des sections est identique pour chaque patient.

### Rédiger une consultation

La première action rapide quitte la page : `/patients/[id]/consultation` est le compte rendu
post-consultation, disposé dans l’ordre où le travail se fait — la note, un point par objectif actif, la
consigne permanente et le résumé vivant préremplis avec ce qui est en vigueur, des liens vers les
sections recommandations, suppléments et essentiels, et la note de préparation pour la fois suivante. Un seul
enregistrement écrit le tout dans une seule transaction et consigne un seul événement d’audit nommant ce qui a changé ;
les actions par carte de la page patient restent la voie de modification entre deux consultations.

Le formulaire est conservé dans le stockage local du navigateur pendant la saisie et restauré à la
réouverture de l’écran — les liens vers les sections du protocole quittent la page puis y reviennent, et un brouillon qui
ne survivrait que pour la note perdrait le reste. Il est effacé dès qu’un enregistrement réussit, et rien de ce brouillon
n’atteint le serveur ni un autre appareil.

## La table des aliments dans la console

`/aliments` est la seule surface de l’administration qui ne concerne pas une personne en particulier. Elle lit la
table de composition ANSES Ciqual 2025 — 3 484 aliments, 74 constituants — importée dans `foods` et
`food_nutrients` par `pnpm ciqual:import`, un script de maintenance pointé sur l’export téléchargé
depuis l’ANSES. L’export brut n’est pas dans le dépôt ; un sous-ensemble dérivé l’est, comme jeu de test
des tests de service.

La page est en lecture seule : elle n’a donc aucune action serveur à garder deux fois et n’écrit rien dans la piste
d’audit. Elle vit tout de même dans le groupe `(admin)`, ce qui la réserve aux opérateurs. Les valeurs sont
affichées dans la notation propre de l’éditeur — `traces`, `< 0,01`, et « — » là où un constituant n’a jamais été
déterminé — car une page qui arrondit cela en nombres affirme quelque chose que la table ne dit pas.

La licence (Licence Ouverte 2.0, Etalab) exige que la source soit nommée partout où ses données sont
affichées ; la ligne d’accueil de la console et les deux pages `/aliments` la portent donc. L’édition, le DOI et les
conditions figurent dans [décisions](/technical/decisions).
