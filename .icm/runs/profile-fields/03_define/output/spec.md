## Problem

`patient_profiles` carries most of brainstorm § A (PATIENT_PROFILE), but four of its base facts are
either missing or merged into prose. `constraints` is documented as "Allergies, intolerances,
medical constraints" — one free-text blob holding three different kinds of fact. Allergies are
safety (mandatory exclusions); intolerances are comfort; medical constraints are neither. A recipe
or recommendation filter has to treat them differently, and none of them should need recovering
from a paragraph. Dietary regime, whether the patient likes cooking, and the food budget are absent
altogether, so nothing downstream can keep suggestions realistic or simple enough.

This is stub 2 of the `patient-record` epic: the manual record Morgane runs a consultation from,
built as permanent data layer now so the AI round later changes read and write sites rather than
migrations. `business/initiatives` names the terrain-first, manual-before-AI sequencing this
follows; the epic's decisions of record (`.icm/intake/patient-record/breakdown.md § Decisions`)
bind it — admin + data layer only, no patient-facing change.

## Proposed change

Five new columns on `patient_profiles`, each surfaced in the admin profile form and carried through
the model, the zod input shape and the create/update paths:

- **`dietary_regime`** — free text (végétarien, sans gluten, …), with a `datalist` of common regimes
  as a typing aid only. Not an enum: § 7 of the brainstorm forbids fine-grained fields, and a closed
  set would freeze vocabulary that is still Morgane's to invent.
- **`allergies`** — free text, split out of `constraints`. The safety row: mandatory exclusions.
- **`intolerances`** — free text, split out of `constraints`. The comfort row.
- **`likes_cooking`** — a small closed set (`cookingAffinity`) in
  `packages/services/src/shared/patient.ts`, rendered as a Select. § A asks yes/no; the constant
  carries a third value so "un peu" costs a constant rather than a migration if Morgane wants it.
- **`food_budget`** — free text. Coarse bands (serré / moyen / confortable) are Morgane's call to
  make after she has filled profiles by hand; free text does not pre-empt it, and bands can arrive
  later as `datalist` suggestions with no migration.

`constraints` keeps its column, its content and its position, and its description narrows to what
remains once allergies and intolerances have their own homes: **medical constraints that are
neither**. The schema comment, the model doc comment and the form's French hint all narrow together.

Existing `constraints` prose is **not** migrated and **not** parsed. Current content stays exactly
where it is; Morgane redistributes it into the new fields as she next touches each patient (10–15
profiles). The new columns are `not null default ''` (or nullable, for `likes_cooking`), so every
existing row is valid the moment the migration runs.

Decisions taken at Define (Jamie, 2026-09-02) on the stub's open questions: regime = free text with
suggestions; likes cooking = tri-state constant; budget = free text. The fourth — whether
`preferences` splits into liked / disliked foods — is **not** answered here; it is out of scope
below and stays Morgane's.

## Acceptance criteria

- [ ] `patient_profiles` gains `dietary_regime`, `allergies`, `intolerances`, `likes_cooking` and
      `food_budget`, with a checked-in migration generated by `pnpm db:generate` that applies to a
      database holding existing rows without manual intervention.
- [ ] `PatientProfile` in `packages/services/src/db/models/patient-profile.ts` carries the five new
      fields, and `likes_cooking`'s type derives from a `cookingAffinity` constant in
      `packages/services/src/shared/patient.ts` — the same constants-derive-the-type pattern as
      `patientSexes` and `consentChannels`.
- [ ] The patients service validates and persists all five on create and on update: a partial update
      that omits a field leaves it untouched, and `""` clears a text field, matching the existing
      `nullableText` behaviour.
- [ ] The admin profile form (`/patients/new` and `/patients/[id]`) shows all five fields with
      French labels and hints, saves them through `savePatientAction`, and re-renders them on reload.
- [ ] Dietary regime offers common regimes as `datalist` suggestions while still accepting any typed
      value; likes-cooking is a Select over `cookingAffinity` with French labels in
      `apps/admin/components/patients/vocabulary.ts`; food budget is a plain text input.
- [ ] `constraints` is unchanged in name, type and stored content, and its description — schema
      comment, model comment and form hint — now names only the medical constraints that are neither
      allergy nor intolerance.
- [ ] A profile edit that changes any of the five fields writes the existing `patient.updated` audit
      entry, unchanged in shape.
- [ ] The patients service tests cover round-tripping the five new fields through create and update
      against the in-memory client, including the tri-state and the not-recorded case.
- [ ] `/p/[token]` renders exactly as it does today — no new field appears on the patient link, and
      the existing `constraints` / `preferences` sections still render their stored text.

## Out of scope

- **Splitting `preferences` into liked / disliked foods.** § A has them as two rows; whether that
  matches how Morgane writes is her call, and it is not this stub's scope. Raised below.
- **Migrating or parsing existing `constraints` prose.** No backfill script, no heuristic split.
  Morgane redistributes by hand as she touches each profile.
- **Surfacing the new fields on `/p/[token]`.** Whether the patient sees their regime, allergies or
  budget is the `patient-surface` epic's call (epic decision 4: this epic is admin + data layer
  only).
- **Any patient-link change** — no token, routing, visibility or consent change.
- **Coarse budget bands as a closed set**, and any recipe/recommendation filtering that reads these
  fields. This stub lands the data and the entry surface; the filters are a later round.
- Structured anamnesis, goals, summary and supplements — stubs 3–6 of the epic.

## Open questions

- **Does `preferences` want splitting into liked / disliked foods?** § A lists them as two rows;
  today it is one prose field. Morgane's call, and a follow-up stub if she wants it — nothing in
  this run depends on the answer, and no code here assumes either shape.
- Coarse budget bands (serré / moyen / confortable) remain available later as `datalist`
  suggestions over the same free-text column, if Morgane finds she writes the same three words.
  Non-blocking: no migration is needed to adopt them.
