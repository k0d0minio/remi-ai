# Build notes: recipe-library

- commits: see the branch — data layer, v1 retirement, admin library, patient assignments
- demo: none (Design was skipped; the spec's `demo:` is `none`)

## What changed

### The data layer — `packages/services`

- `db/schema.ts`: `recipes` (title, prose `body`, `tags text[]`, `archived_at`, no patient FK — the
  first content table belonging to no patient) and `patient_recipe_assignments` (`note`,
  `assigned_on`, `archived_at`). The two foreign keys differ deliberately: `patient_id` cascades,
  `recipe_id` is `on delete restrict`, which is "archive, never delete" expressed in the database
  rather than trusted to the service.
- `db/migrations/0005_smooth_the_leader.sql`: generated by `pnpm db:generate`, additive only — two
  `CREATE TABLE`s and two constraints, nothing touching existing rows.
- `db/models/recipe.ts` rewritten as the V2 model; `db/models/recipe-assignment.ts` added, carrying
  `AssignedRecipe` (the assignment + its recipe) because a client component renders the pair and
  client code may only take types from `/shared`.
- `db/services/recipes/`: list active (tag + title filters), list archived, list tags in use, get,
  create, update, archive/restore, count assignments. **No delete function exists** — the library
  archives, and the FK enforces it.
- `db/services/recipe-assignments/`: list active/archived for a patient (each joined to its recipe),
  assign, update note and date, archive/restore, remove. A second _active_ assignment of one recipe
  to one patient returns `conflict`; the same recipe assigned again after an archive is allowed,
  because those dated rows are the WEEKLY_ADAPTATION trail.
- Tag filtering and the title search run in the service, not at the seam: the seam speaks
  equality-and-limit, and pushing array-contains down would tie every adapter to Postgres.
- Registered in the `neon.ts` collection registry; exported from `@remi/services/server`; the models
  re-exported through `/shared`. Nine `recipe.*` actions added to the closed `auditActions`.

### Retiring v1

`business/scope` lists rigid weekly plan generation as deliberately replaced, so the v1 recipe
surface is deleted rather than parked (owner decision, recorded in the spec):

- Gone: `models/recipe.ts`'s v1 shape and `Ingredient`, `models/meal.ts` (`Meal`, `MealSlot`,
  `MealStatus`), `apps/web`'s `/meals` route, `lib/fixtures/meals.ts`, `lib/queries/meals.ts`, the
  meals nav entry and its icon, and the `meals` content block in both locales.
- `formatWeekday` went with it: the meals screen was its only consumer, and an export with no
  consumer is a rename-blocker (CONVENTIONS.md § leanness).
- Two publish-dialog strings promised the patient "meals and steps in their space". The meals screen
  no longer exists, so they now say "steps" — copy naming a deleted surface is a lie the UI tells.
- `apps/demo` keeps its own local mock `Recipe`: separate vocabulary, mock-only sandbox, out of this
  stub's remit.

### The console — `apps/admin`

- A « Recettes » nav entry beside Patients; `/recipes` (library rows, tag filter built from the tags
  in use, title search, create form, archived section) and `/recipes/[id]` (edit, archive/restore,
  and the count of patients currently holding it).
- On `/patients/[id]`, a Recettes card after the pantry card: current assignments with the dish, her
  note and the date, inline edit of note and date, archive; an assign-from-library picker over the
  **active** library only; and a « Recettes précédentes » section with restore.
- Server actions in `lib/recipes/actions.ts` (library) and `lib/patients/actions.ts` (assignments),
  each re-asserting `requireOperator()` and writing its audit row after the success branch. The nine
  `recipe.*` actions carry French labels and intents in the console's audit vocabulary.

## Notes for Verify

- **The v1 retirement is the risky half of this diff**, not the new tables. It deletes a live route
  and both locales' content for it. Worth checking on the preview that `/today`, `/steps`, `/plan`
  and `/p/[token]` still render, and that the patient nav has three entries rather than four.
- The service tests were run locally (`vitest`, 122 passing) because a wrong test costs a CI round
  trip. Format, lint, typecheck and build were **not** run locally — the factory owns them.
- `countRecipeAssignments` and the tag filter read the whole collection and filter in the service.
  Correct at 10–15 patients and tens of recipes, and the seam is why it is written this way; it is
  the first thing to revisit if the library ever reaches thousands of rows.
- The in-memory test client compares filter values with `===`, so it cannot express "tags contains
  x". That is why the tag filter is tested through `listRecipes` rather than through the seam.
- Three open questions from the spec are unanswered by design (variant duplication, week marking,
  which tags). Nothing built here assumes an answer to any of them.
